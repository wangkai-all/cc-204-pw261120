# 共享单车供需分析台（本地网页 · 合成数据演示）

把**车辆位置快照、借还订单、调度记录**三类原始数据合并，按站点还原一天内可用车辆的变化，并区分
**缺车、满桩、数据断档、快照不一致**，提供基于历史同类时段的**潜在需求估算**与**调度方案对比**。
全部数据由固定随机种子合成，**不需要地图或真实运营数据**。

## 运行

```bash
npm start          # 或 node tools/serve.js
# 浏览器打开 http://localhost:8123
```

无需构建、无第三方依赖，纯原生 HTML/CSS/SVG/JavaScript，直接用浏览器打开 `index.html` 也可。

## 测试

node tools/smoke.js    # 数据与分析引擎的关键不变量

## 数据模型与关键口径

| 记录 | 含义 |
|---|---|
| `snapshots` | 15 分钟车辆位置快照，含刻意注入的传感器漂移（drift）、卡死（stale）与全局断档 |
| `orders` | **真实**成功借还订单。估算订单永远不写入此表 |
| `attempts` | 借/还尝试流，含缺车失败（empty）与满桩失败/改道（full）——“没订单≠没需求”的证据 |
| `dispatches` | 调度记录（含站点合并划转、容量调整），只改变车辆位置，**不计入用户还车** |
| `history` | 同星期历史小时汇总，受缺车约束的样本会被标记并在估算时剔除 |
| `plans` | 三个调度方案（A 实际基线 / B 早高峰保供 / C 午间再平衡） |

### 库存如何重建

1. 以当日首快照为锚点，按「还车 → 调度 → 借车」顺序重放窗口内事件；
2. 每个快照点对账：事件预测值与快照读数不一致即记录差异并以快照纠偏；
3. 相邻快照间隔超阈值判为**数据断档**，断档内的库存是事件推演值、未经快照核实，
   状态只标为「存疑」，与「已核实缺车」分开；
4. 站点合并、容量变化按 `effectiveDate` 生效；凌晨/夜间调度保留在事件清单可追溯。

### 潜在需求估算（独立结果，不回写订单）

对每个缺车时段，取同站点、同星期、同小时且**未受缺车约束**的历史样本，用平均需求率乘以缺车时长，
扣除已观测成功借车得到点估计；以历史最小/最大率给出不确定范围，断档内缺车下界取 0、上界放宽。
所有假设与范围都在页面上显式展示。

### 校正前 vs 校正后

- **校正前（naive）**：只信 15 分钟快照，缺快照时段当作状态不变，不识别断档、不对账；
- **校正后（corrected）**：融合订单+调度事件对账，区分已核实/存疑缺车，单独统计断档。

## 合成数据刻意演示的现象

- ST01 凌晨被过量回收 → 早高峰**缺车**与流失借车；
- ST02 容量由 25 降到 20、午后还车集中 → **满桩**与改道；
- ST04 关停并入 ST03（合并划转是调度，不是用户还车）；
- 聚焦日 09:30–11:00 全局**数据断档**；
- ST01/ST05 传感器漂移、ST02 传感器卡死等**快照不一致**；
- 三个调度方案重放后缺车时长、失败借车、估算流失的差异。
